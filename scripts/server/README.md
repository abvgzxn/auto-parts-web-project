# Развёртывание Wellcar

Этот каталог — локальная копия серверного скрипта. Изменение файлов здесь само по
себе ничего не устанавливает на VPS. Команды установки ниже предназначены для
администратора; локальные тесты их не выполняют.

## Архитектура и политика SHA

Существующий `ssh-deploy.sh` принимает через `SSH_ORIGINAL_COMMAND` только
`deploy <40-символьный SHA>` и вызывает root-owned
`/usr/local/libexec/wellcar/deploy.sh`. Основной скрипт также проверяет аргумент.

**Разрешён только HEAD `origin/main`, полученный при `git clone`. Предки main
не допускаются.** Скрипт сравнивает SHA с `refs/remotes/origin/main^{commit}`,
не загружает переданный SHA отдельно. Это работает с `--depth 1` и исключает
коммиты других веток, кроме совпадающих с HEAD main. При движении main между
запуском CI и clone старый SHA отклоняется; нужно повторить запуск для нового
HEAD. Принадлежность истории определяется состоянием удалённой ветки на момент
clone, а не последующими изменениями main.

`flock` сериализует деплои. Релиз создаётся в
`/var/www/wellcar-deploy/releases/YYYYMMDD-HHMMSS-PID`; выполняются `npm ci`,
lint, build и предварительная HTTP-проверка Next.js на 127.0.0.1:3001.
Затем атомарно заменяется ссылка `current`, перезапускается `wellcar` и
проверяется HTTP на 3000. ERR/INT/TERM после начала переключения вызывают одну
попытку вернуть старую ссылку, перезапустить службу и проверить HTTP.
Сохраняются коды исходной ошибки, INT=130, TERM=143. При отсутствии старого
релиза новый current остаётся для диагностики; требуется администратор.

После успешной production-проверки сохраняются пять релизов всего: текущий,
предыдущий и самые новые оставшиеся (по имени с UTC-временем). Если предыдущий
старый, он занимает одно из пяти мест. При меньшем числе сохраняются все.
Кандидат на удаление должен быть непосредственным каталогом releases с указанным
форматом имени, реальным каноническим путём, каталогом `.git` и `package.json`.
Ссылки и остальные записи пропускаются. Ошибка очистки выводит предупреждение,
не меняет успех деплоя и не запускает откат. Неудачные сборки могут остаться до
следующей успешной очистки. Каталоги такого формата с `.git` и `package.json`
считаются релизами: посторонние данные нельзя хранить под этой структурой.

## Зависимости и установка администратором

Нужны Bash, GNU coreutils (включая realpath и `rm --one-file-system`), util-linux
`flock`, Git, OpenSSH, Node.js/npm подходящей проекту версии, curl, iproute2
`ss`, grep, systemd и sudo. Нужны доступ к GitHub через существующий SSH alias,
место для сборки, существующая служба wellcar и разрешение deploy на
`sudo -n /usr/bin/systemctl restart wellcar`.

BASE и releases должны существовать, быть каноническими каталогами без симлинков.
Пользователь deploy должен иметь право писать в них. `current` может отсутствовать
при первой установке, иначе должен ссылаться на существующий релиз внутри releases.
Не изменяйте дерево релизов параллельно со скриптом: flock защищает только
участников, использующих тот же lock. Сам скрипт и родительские каталоги libexec
должны быть недоступны deploy для записи.

После локальной проверки администратор переносит проверенный файл, например в
`/tmp/wellcar-deploy.sh`, и выполняет на сервере:

```bash
sudo bash -n /tmp/wellcar-deploy.sh
sudo cp -a /usr/local/libexec/wellcar/deploy.sh /root/wellcar-deploy.sh.before-hardening
sudo install -o root -g root -m 0755 /tmp/wellcar-deploy.sh /usr/local/libexec/wellcar/deploy.sh.new
sudo mv -Tf /usr/local/libexec/wellcar/deploy.sh.new /usr/local/libexec/wellcar/deploy.sh
```

Не перезаписывайте сохранённую резервную копию при повторной установке.
SSH-конфигурация, wrapper и unit в рамках этой работы не меняются.

## Проверка

Из корня репозитория:

```bash
bash -n scripts/server/deploy.sh
python3 scripts/server/test_deploy.py
```

Нужен Python 3. Тесты копируют скрипт с заменой фиксированного BASE на временный
каталог; production-скрипт не поддерживает переопределение пути через окружение.
Git, npm, curl, sudo, ss, sleep, flock, mv и rm заменены моками. Настоящие clone,
сборка, HTTP, SSH, systemd и удаление серверных каталогов не выполняются.
Моки не подтверждают корректность серверных прав, реальную блокировку flock,
GitHub refs, здоровье приложения или поведение systemd. Эти проверки проводит
администратор отдельно в согласованное окно; production dry-run отсутствует.

## Откат и восстановление скрипта

При сбое смотрите сообщения об исходной ошибке и результате отката,
`readlink -f /var/www/wellcar-deploy/current`, журнал wellcar и test-server.log.
Успешный HTTP-ответ проверяет только корень сайта, не все функции приложения.
SIGKILL, отключение питания и падение ОС ловушками не обрабатываются.

Для ручного отката администратор должен исключить параллельный деплой
(держать `/var/www/wellcar-deploy/.deploy.lock` через flock), проверить выбранный
существующий релиз внутри releases, создать временную ссылку в BASE и атомарно
заменить ею current через `mv -Tf`, затем перезапустить wellcar и проверить HTTP.
Это позволяет вернуть предка main без ослабления политики входного SHA.
Если предыдущего релиза нет или откат завершился ошибкой, состояние нужно
проверить вручную; скрипт не гарантирует восстановление службы.

Для восстановления старого **скрипта** сначала исключите активные деплои, затем:

```bash
sudo bash -n /root/wellcar-deploy.sh.before-hardening
sudo install -o root -g root -m 0755 /root/wellcar-deploy.sh.before-hardening /usr/local/libexec/wellcar/deploy.sh.restore
sudo mv -Tf /usr/local/libexec/wellcar/deploy.sh.restore /usr/local/libexec/wellcar/deploy.sh
```

Восстановление скрипта не переключает current и не возвращает уже удалённые
релизы. Перед установкой убедитесь, что резервная копия — действующий скрипт,
без случайно вставленного вывода терминала.
